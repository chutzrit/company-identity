# 회사 방향성 인터뷰

## 한 번에 질문 하나

한 메시지에는 질문을 하나만 담는다. 답을 받은 뒤 다음 질문을 한다.

- `질문 1`·`질문 2`처럼 번호를 매겨 여러 질문을 묶지 않는다.
- 비전 한 줄과 가치 충돌처럼 서로 다른 결정을 한 메시지에 함께 묻지 않는다. 앞의 답이 뒤 질문의 상황과 예시를 바꾸기 때문이다.
- 직전 답변을 어떻게 기록했는지 1~2줄로 알린 뒤 질문 하나를 이어 붙이는 것은 괜찮다.
- 사용자가 한 번에 여러 내용을 답하면 모두 반영하고 이미 답한 질문은 건너뛴다.

## 첫 질문

자료가 없는 첫 호출이면 한 문장으로 시작하고 어떤 일을 하는지부터 묻는다. 이미 제공된 내용은 생략한다.

```text
어떤 회사를 만들고 싶은지부터 짧게 정리해 볼게요.

어떤 일을 하나요? 누구에게 무엇을 제공하는지 편하게 적어 주세요.
```

답변에서 빠진 내용만 이어서 하나씩 묻는다. 순서는 고객이 겪는 문제, 고객의 현재 해결 방식, 회사명·기존 소개 자료다.
회사명·자료 위치에는 예시를 억지로 붙이지 않는다. 사업이나 고객 설명을 어려워하면 답변 형태를 짧게 보여준다.

## 구체화 질문에는 예시를 먼저 붙이기

사용자가 “어렵다”고 말할 때까지 기다리지 않는다.
가치·차별점·비전·우선순위·거절 조건·업무 기준을 물을 때는 질문마다 다음 형식을 사용한다.

1. 이번에 결정할 내용 한 가지를 쉬운 질문으로 묻는다.
2. 이미 파악한 사업에서 일어날 상황을 한 문장으로 보여준다.
3. 서로 다른 선택을 보여주는 답변 예시 2~3개를 짧은 `text` 코드 블록에 넣는다.
4. 예시를 고치거나 섞어서 답할 수 있게 한다. 해당되는 예시가 없거나 아직 미정이어도 된다.

구체화 질문도 한 메시지에 하나만 한다. 한 질문에 여러 결정을 숨기지 않는다.
추상적인 전문용어 풀이보다 사용자가 답할 수 있는 문장 형태를 보여준다.
질문을 구성할 때는 [인터뷰 템플릿](interview-template.md)을 읽는다. 답변에 따른 후속 질문과 문서 반영 방식이 필요하면 [인터뷰 예시](interview-examples.md)를 읽는다.

## 예시를 만드는 기준

- 사용자가 말한 고객·상품·업무를 소재로 삼는다. 참고 예시의 업종을 그대로 가져오지 않는다.
- 사업을 모르면 먼저 묻거나 업종을 전제하지 않는 예시를 쓴다.
- 선택마다 얻는 것과 감수하는 것이 다르게 만든다. 한 선택만 좋아 보이는 유도 질문을 피한다.
- 기존 확정 규칙이 있으면 그 안에서 가능한 예시를 든다. 이미 금지한 일을 일반 선택지로 되살리지 않는다.
- 금액·기간·실적·제공 서비스는 확정 사실처럼 넣지 않는다. 구체적인 수치가 꼭 필요하면 가정임을 밝힌다.
- 제시한 예시는 사용자가 선택·수정하기 전까지 제안이다. 이를 확정 문서에 넣거나 대신 골라 진행하지 않는다.
- “2번처럼 하되 일정은 고객과 협의”라고 답하면 그 수정까지 반영한다. 다른 예시의 내용은 합치지 않는다.
- 이전에 답한 사실을 재질문하지 않는다. 답하기 어렵다고 하면 질문을 더 작게 나누고 더 가까운 상황으로 바꾼다.

## 대화에서 채울 내용

아래 순서는 질문 설계용이다. 전체 설문지를 한 번에 제출하지 않는다.
새 사업이면 바라는 모습과 가설을, 운영 중이면 실제 고객 사례와 개선할 점을 구분해 듣는다.

| 주제 | 알아낼 내용 | 구체화할 방향 |
|---|---|---|
| 고객·문제 | 우선 고객과 고객이 겪는 상황 | 고객이 지금 어떻게 해결하며 어디에서 막히는가 |
| 선택 이유 | 고객이 다른 방식 대신 우리를 선택할 이유 | 직접 하기·기존 업체 등과 비교해 무엇을 다르게 제공할 것인가 |
| 존재 이유 | 지금 고객을 위해 하는 일 | 해결할 문제와 일상적인 제공 방식 |
| 비전 | 앞으로 만들고 싶은 변화와 이를 담은 비전 한 줄 | 일이 잘됐을 때 고객의 생활·업무가 어떻게 달라지는가 |
| 가치·강점 | 지킬 태도와 실제 잘하는 일 | 가치가 드러나는 행동과 확인 가능한 근거 |
| 우선순위 | 두 가치가 충돌할 때 먼저 지킬 것 | 구체적인 상황에서 무엇을 얻고 무엇을 양보하는가 |
| 지양점 | 수익이 나도 피할 일·약속 | 거절 조건과 대신 제안할 수 있는 범위 |
| 업무 적용 | 디자인·영업·콘텐츠의 판단 기준 | 작업에서 할 행동과 결과물에서 확인할 증거 |

선택 이유가 아직 검증되지 않았으면 `가설`로 남긴다. 경쟁사 약점이나 시장 사실을 만들어 뒷받침하지 않는다.
사업 단계와 가까운 목표는 우선순위를 정하는 데 필요할 때만 묻는다. 기한·매출·가치 개수를 임의로 정하지 않는다.
말투·색상·로고는 이번 업무와 관련되거나 사용자가 요청할 때만 확장한다.

## 비전 한 줄

회사가 만들고 싶은 변화를 한 문장으로 정한다. 방향성 문서의 `존재 이유와 비전` 맨 위에 적고, 이후 업무에서 가장 먼저 참고하는 문장이다. 이미 파악한 변화를 문장으로 고르는 단계이므로 상황 설명은 생략할 수 있다.

- 첫 질문에 넣지 않는다. 사업·고객·문제를 파악한 뒤 만들고 싶은 변화를 물을 때 함께 다룬다.
- 이미 쓰는 비전 문장이 있는지 먼저 묻는다. 있으면 표현을 다듬지 않고 그대로 받는다.
- 없으면 지금까지의 답변만으로 한 줄 후보 2~3개를 만들어 `text` 코드 블록으로 보여준다. 후보마다 강조하는 변화가 다르게 만들고, 사용자가 말하지 않은 시장·규모·수치를 넣지 않는다.
- 사용자가 고르거나 고친 문장만 기록한다. 아직 정하고 싶지 않으면 `미정`으로 남기고 인터뷰를 계속한다.
- “세상을 이롭게”처럼 어느 회사에나 맞는 문장이면 누구의 무엇이 달라지는지 한 번 더 묻는다.

## 가치에서 사규로 연결

각 가치를 아래 관계로 구체화한다.

`지키려는 가치 → 상황에서 할 일·피할 일 → 결과물에서 확인할 근거`

- 사용자가 이미 구체적으로 정한 행동은 그대로 활용한다.
- 추상적인 답이라면 사업에 맞는 서로 다른 행동 예시를 주고 선택·수정을 받는다.
- 한 행동을 택했다고 해서 연결 가능한 다른 금지·정책까지 확정하지 않는다.
- 새 제안만 확인한다. 이미 결정한 내용을 형식적으로 재승인받지 않는다.

## 기존 문서가 있을 때

호출만 받으면 현재 기준 2~3줄, 중요한 빈틈 최대 2개, 목적 질문 하나로 답한다.
구체적인 요청이 있으면 해당 항목과 관련 규칙부터 읽는다.

예를 들어 “영업팀 기준만 보강해 줘”라면 현재 영업 기준에서 빠진 선택을 구체적인 상황과 답변 예시로 묻는다. 고객·비전 전체를 다시 인터뷰하지 않는다.
소개서에 명시된 사실, 사용자 발언, 에이전트 제안을 구분한다. 문서와 최근 발언이 충돌하면 어떤 내용을 반영할지 확인한다.

## 충분한 답변이 모이면

- 방향성 요약과 중요한 선택을 보여주고 수정 의견을 반영한다.
- 문서 구조는 [documents.md](documents.md)를 따른다. [결과물 양식](output-templates.md)에 답변을 반영해 방향성·사규·프로젝트 작업 지침을 함께 작성한다.
- [scenarios.md](scenarios.md)의 상황 질문으로 실제 선택에 쓸 수 있는지 검증한다.
- 빠진 내용이 결정을 막지 않으면 `미정`으로 남긴다.
- 중간 저장을 요청하면 확인된 내용과 이어서 답할 질문을 초안에 남긴다.
- 최종 저장 단계에서는 별도 요청 없이 문서 3종과 경로 설정을 저장한다. 작업 지침은 회사 기준을 적용하는 내용으로 완성하며 미래 프로젝트 정보를 채우기 위한 별도 질문은 하지 않는다.
